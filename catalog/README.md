# Catalog

`catalog/` contains generated discovery projections for Fabric Ecosystem.

```text
Catalog = derived discovery projection
Catalog != Fabric semantic truth
Catalog != registry
Catalog != package manifest authority
Catalog != runtime state
```

Fabric and Rust source own Resource APIs, Components, Adapters, relations,
Composition graphs, Host truth, and runtime behavior. Cargo manifests own Cargo
package metadata. Repository topology owns source placement. The Catalog
projects selected discovery facts from those owners.

## Generated Views

- `index.json`: machine-readable Catalog v2.
- `index.md`: human-readable navigation generated from the same in-memory model.

Both files are generated by:

```sh
cargo run -p fabric-ecosystem-catalog-tool -- write
```

Check committed output without mutation:

```sh
cargo run -p fabric-ecosystem-catalog-tool -- check
```

Workspace tests also run the same drift check.

Validate the committed machine document without source discovery:

```sh
cargo run -p fabric-ecosystem-catalog-tool -- validate
```

These commands have distinct responsibilities:

- `write`: source-aware; regenerates and writes `catalog/index.json` and
  `catalog/index.md`.
- `check`: source-aware; regenerates expected output and compares it with the
  committed projection without mutation.
- `validate`: source-independent; reads committed `catalog/index.json` and
  verifies that it is an internally valid canonical Catalog v2 document.

## Consuming Catalog v2

`index.json` is the machine-readable Catalog contract. Local query commands read
the committed JSON projection directly; they do not run Cargo metadata, inspect
Rust/Fabric source, or materialize runtime state.

```sh
cargo run -p fabric-ecosystem-catalog-tool -- list
cargo run -p fabric-ecosystem-catalog-tool -- list-kind package
cargo run -p fabric-ecosystem-catalog-tool -- list-kind instance
cargo run -p fabric-ecosystem-catalog-tool -- list-category networking
cargo run -p fabric-ecosystem-catalog-tool -- show packages/networking/http
cargo run -p fabric-ecosystem-catalog-tool -- show-package onoal-fabric-package-networking-http
cargo run -p fabric-ecosystem-catalog-tool -- deps compositions/web/http-server
cargo run -p fabric-ecosystem-catalog-tool -- dependents packages/networking/tcp
```

Query commands show the committed projection as-is. `check` remains the command
that validates whether committed output is fresh relative to repository/Cargo
sources.

## JSON V2

The current generated `index.json` uses:

```json
{
  "schemaVersion": 2,
  "artifacts": []
}
```

Each artifact entry contains discovery/navigation fields only:

- `kind`: repository artifact kind derived from path: `package`, `host`,
  `composition`, `instance`, or `example`.
- `category`: open repository navigation category where the path has one
  (`packages/<category>/...`, `compositions/<category>/...`).
- `path`: repository-relative artifact source path.
- `cargoPackage`: Cargo package name from Cargo metadata.
- `version`: resolved Cargo package version from Cargo metadata.
- `description`: Cargo package description from Cargo metadata.
- `publishable`: derived from Cargo `publish` metadata.
- `readme`: repository-relative README path when `<artifact>/README.md` exists.
- `dependencies.normal`, `dependencies.development`, `dependencies.build`:
  direct Cargo dependency edges to other cataloged ecosystem artifacts, grouped
  by Cargo dependency kind and referenced by artifact source path.

There is no Catalog-owned artifact ID in v2. Repository-relative path and Cargo
package name already have concrete owners.

Catalog v2 is a strict canonical document contract, not an open property bag.
Readers reject unknown top-level fields, artifact fields, and dependency-group
fields. Persisted vocabulary such as `maturity`, `status`, `tags`, `provides`,
or `requires` cannot be added to a v2 document as optional ignored data.

Artifact paths are canonical repository-relative slash-separated paths matching
the supported topology exactly. The artifact `kind` and `category` must agree
with the path:

```text
packages/<category>/<artifact>        -> kind package, category <category>
hosts/<artifact>                      -> kind host, no category
compositions/<category>/<artifact>    -> kind composition, category <category>
instances/<category>/<artifact>       -> kind instance, category <category>
examples/<artifact>                   -> kind example, no category
```

Paths must not be absolute, contain empty, `.` or `..` segments, use
backslashes, or use unsupported topology depth. When `readme` is present, it is
exactly `<artifact path>/README.md`.

Artifacts are sorted lexicographically by `path`. Dependency path arrays are
sorted lexicographically inside each dependency group. Readers reject malformed
or non-canonical order rather than silently normalizing it.

## Historical V1 Reader Support

The reader accepts strict canonical Catalog v1 and strict canonical Catalog v2.
These are separate contracts.

Catalog v1 kinds are:

```text
package
host
composition
example
```

Catalog v2 adds exactly:

```text
instance
```

A v1 document cannot contain an `instance` artifact or `instances/...`
topology. The tool does not silently reinterpret v1 as v2.

## Classification

Catalog v2 classifies workspace Cargo packages by repository path:

```text
packages/<category>/<artifact>        -> package
hosts/<artifact>                      -> host
compositions/<category>/<artifact>    -> composition
instances/<category>/<artifact>       -> instance
examples/<artifact>                   -> example
```

`tests/*` and `tools/*` are verification/tooling infrastructure and are not
cataloged ecosystem artifacts.

Repository artifact kind and category are navigation facts. They are not Fabric
semantic kinds.

## Schema Evolution

`schemaVersion: 2` means the document satisfies the complete v2 structural
contract. Catalog v2 exists because `instance` is a new persisted artifact kind.
Hardening reader enforcement of invariants already emitted by a generator does
not require a schema-version bump.

Data changes that do not change the persisted shape or field meaning do not
require a new schema version. Examples include adding or removing artifacts,
changing descriptions or versions, changing publishability, introducing a new
category value, adding or removing Cargo dependency edges, or a README appearing
or disappearing.

Changes that alter persisted shape or meaning require a new schema version.
That includes adding even an optional persisted field, removing or renaming a
field, changing a field type or semantic meaning, changing dependency-group
structure, adding or removing a persisted artifact kind, changing the
path/category structural contract, adding an extension/custom-field mechanism,
or changing identity/reference semantics.

New query features that derive results from existing v2 fields do not require
schema evolution. Generator refactoring or performance work also does not
require schema evolution when generated v2 bytes and meaning remain unchanged.

## Dependency Meaning

Catalog dependency edges are Cargo dependency/navigation edges. They are not
Fabric relations, Resource requirements, Component dependencies, Composition
graphs, runtime dependencies, or semantic ownership claims.

External dependencies such as `onoal-fabric`, `rusqlite`, `httparse`, and
cryptographic crates are excluded unless they are themselves cataloged
repository artifacts.

## Non-Goals

Catalog v2 does not contain:

- Resource, System, Component, Adapter, Augmentation, Config, or relation IDs;
- handwritten `provides` / `requires` fields;
- maturity, stability, quality, status, recommendation, tag, or keyword
  taxonomies;
- runtime discovery or materialization results;
- generated timestamps, hostnames, user names, random IDs, absolute paths, or
  dirty-state information;
- remote registry, website, HTTP service, publication workflow, or package
  installer behavior.

Future views may consume a canonical Fabric definition projection if Fabric
exposes one. Until then, Catalog deliberately avoids Rust macro/source
introspection.
